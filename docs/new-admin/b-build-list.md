# Design B: what it needs, line by line

- **Lines in total: 115**
- **Lines Core already supports: 84** (marked **exists**)
- **Lines needing something new in Core: 31** (27 marked **partly**, 4 marked **new**)

How to read this list:

- Images are `/mnt/project-files/clean-room/out/b/NN-….png`; only the number is given.
- "exists" means Core already holds the data or does the action; the page or window in the admin is new either way, because B replaces today's admin.
- "Core today" names the place in the code (file:line, paths from the repository root).
- Words: B says "brokerage" for what Core calls a **tenant**, and "website" for a **site**. Record types use their formal names, with B's word after them.
- B has no Records, Flow, Events, Manual sync, Failed forms, CRMs or Settings page, no list of signed-in devices, and no recompute or record check. The things those pages do today are not in this list.

## Flags against Core's hard rules

- **CRM write (lines 28, 29, 114):** "Resend forms" sends visitors' forms to the brokerage's live Vitec. In the product, this is the existing "Send again". It runs on the live service only, under every form rule (test mode, the 24-hour repeat window, one send in flight). Building or testing it must never send to a target Patric has not confirmed as a test system (AGENTS.md, Stop and ask). No other line writes to a CRM: the login test, the office check, the retries and "Reload all data" only read.
- **The seam (lines 27, 31–33, 38, 41, 42, 51, 56, 64, 71–74, 89, 91, 105–111):** B writes "Vitec" and Vitec's own ideas (live versus QA, customer or group id, "Webbplats", the first notice, the notification address) on general pages. The engine and its admin API may not name a CRM (CI block 2), so all of these words and states must come from adapters/vitec. Several have no channel in the adapter API today: the first-notice state, load progress and "first load done", "office check done" and "office added", a check that names the records it found, Inbox cards with their own buttons, and a solved state for problems the adapter reports. Each of those is a change to engine/adapter-api/, a protected path that needs approval.
- **Tenant isolation (line 73), a concern rather than a break:** the secret in the notification address (VITEC_WEBHOOK_TOKEN) is the same for every live Vitec connection. B tells the admin to give it to each brokerage's Vitec admin, so every customer would hold the key to the one address all customers share. No data crosses tenants (a notification carries no data, and Core fetches only what Vitec lists), but one leak affects every tenant. Line 84 can show a website as "Uses new token" when it has not switched (see that line); that is a truth problem, not an isolation one.
- **"Core applies no logic to CRM data":** no line breaks it. Which offices go on the websites is the Vitec adapter's choice from the CRM's own office group, which the adapter is allowed to make. The counts are by record type and office id, and the status badges come from Core's own state, never from a CRM field.
- **Brief part 2, section 5:** no line contradicts it. Test mode, a switched-off brokerage and maintenance are described the way Core behaves.
